# PHASE 1 — FIX THE REAL ROUTE-LEVEL FAILURE PATH

### A. Wrap intelligence and orchestration route handlers correctly
Inspect all route files involved in Control Tower and related intelligence/recommendation loading, especially:

- `artifacts/api-server/src/routes/intelligence.ts`
- any orchestration/intelligence-related route files used by Control Tower
- any related endpoints triggered by Ingest / recommendation actions / escalation paths

For every async route handler:
- wrap handler body in `try/catch`
- call `next(error)` in `catch`
- ensure errors flow into Express/global error middleware
- remove any dependency on `unhandledRejection` as the expected path for route failures

Do NOT just add broad silent catches.
Do NOT swallow errors.
Do NOT return half-broken success states.

### B. Add route-level structured logging
For these same handlers, log:
- route name
- request purpose
- company/tenant scope if safe
- failing sub-operation
- error message
- whether error is:
  - plan-gating / permission
  - validation
  - DB/query
  - internal runtime

Keep logs structured and useful.

### C. Preserve process-level handlers as last-resort only
Do NOT remove them unless necessary, but ensure the codebase no longer depends on them for ordinary route failures.

The standard must be:
- route failures handled at route level
- process-level handlers are emergency fallback only
