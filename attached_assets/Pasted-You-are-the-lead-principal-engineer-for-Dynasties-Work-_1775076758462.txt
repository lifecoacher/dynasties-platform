- No raw LLM text directly mutates core entities

A. FIRST-CLASS RECOMMENDATION MODEL

Implement or formalize a persistent recommendation system as first-class entities, not embedded/transient output blobs.

Create all necessary schema, migration, ORM, domain model, API, and UI changes for a recommendation system with at minimum:

- shipment_recommendations table
- shipment_recommendation_outcomes table
- optional recommendation_task_links table if needed
- optional recommendation_change_log or use analysis run metadata if sufficient

Each recommendation record should include:
- id
- shipmentId
- companyId
- analysisRunId
- recommendationType
- title
- summary
- explanation
- machineReadableActionPayload
- urgency / priority
- confidence
- severity or operational impact if needed
- status
  - active
  - accepted
  - rejected
  - modified
  - ignored
  - expired
  - superseded
  - suppressed
- supersedesRecommendationId if applicable
- createdAt
- updatedAt
- retiredAt or equivalent

Recommendation types should cover existing Dynasties operational logic where relevant, such as:
- compliance escalation
- document correction
- shipment hold / release
- route adjustment
- carrier switch
- pricing adjustment
- insurance action
- margin warning
- delay mitigation
- customer communication
- claims readiness
- queue reprioritization
- workflow escalation
- operational follow-up task

Do not leave recommendations as display-only artifacts inside shipment AI state.

B. RECOMMENDATION LIFECYCLE / SUPERSESSION RULES

Implement explicit lifecycle logic so recommendations do not pile up chaotically.

Rules must include:
- if a new analysis produces materially equivalent active recommendations, update or preserve correctly without duplication
- if a recommendation is no longer relevant after reanalysis, mark it expired or superseded
- if a recommendation is replaced by a more recent/better version, create proper supersession linkage
- ensure at most the correct set of active recommendations exists per shipment at any given time
- define clear comparison and dedupe logic
- preserve historical traceability

This must be deterministic and tested.

C. OPERATOR OUTCOME TRACKING / DECISION MEMORY

Implement operator actions on recommendations as first-class stored outcomes.

Supported actions:
- accept
- reject
- modify
- ignore if relevant
- optional resolve/complete where needed

Each outcome record must capture:
- recommendationId
- shipmentId
- companyId
- operator userId
- prior recommendation status
- new recommendation status
- operator note
- modified payload if applicable
- timestamp
- contextual metadata useful for later analytics

If “modify” is supported:
- store both original and modified action payload
- reflect this clearly in status/history

This must be reflected in:
- APIs
- UI
- task behavior where appropriate
- audit/history

D. AI-DRIVEN TASK / QUEUE OWNERSHIP

The queue must stop being only exception-driven with AI sprinkled on top.

Implement AI-driven operational work orchestration so recommendations can:
- create new tasks
- update priority on existing tasks
- suppress or close stale tasks when recommendations expire or risk disappears
- reopen tasks when risk returns
- attach machine-readable and human-readable reason metadata to each task
- link task lifecycle to recommendation lifecycle

Every AI-created or AI-updated task should expose:
- recommendationId
- analysisRunId or source analysis reference
- why the task exists
- why the priority is what it is
- current status reason

The queue should materially react to AI state changes.

Examples of desired behavior:
- risk increase -> task priority increases
- compliance escalation recommendation -> task created or escalated automatically
- recommendation expires -> task suppressed or closed if safe
- risk returns after prior resolution -> task reopened

Preserve existing syncTasksFromExceptions behavior, but extend work orchestration so AI recommendations are first-class queue inputs.

E. REPLACE SIMPLE THROTTLE WITH REAL EVENT CONTROL

The current central orchestrator uses a 10-second throttle. This is not sufficient as a production-grade mechanism.

Replace or upgrade this with a real event handling strategy that prevents duplicate or chaotic reanalysis without silently dropping important changes.

Implement a robust approach using some combination of:
- idempotency keys
- event dedupe keys
- event coalescing
- last meaningful input hash
- per-shipment work serialization
- transactional locks where appropriate
- queue job uniqueness
- analysis reason merging during bursts

Requirements:
- rapid repeated domain events must not create duplicate active recommendations or duplicate tasks
- important changes must not be lost
- concurrent triggers must not corrupt AI state
- if several events arrive close together, system should either serialize or intelligently coalesce them rather than blindly skip
- analysis timeline should still make sense after burst scenarios

Document the chosen strategy in code comments and implementation docs.
